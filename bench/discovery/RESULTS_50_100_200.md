## What these results measure (and do not)

- Linux GitHub-hosted Ubuntu 24.04 runner; one Python process and one network namespace per node, connected through veth pairs and a shared Linux bridge with multicast snooping disabled.
- Every condition applied netem **2ms delay at each veth egress**; the 10% condition also added independent 10% random loss at both ends, which can yield a greater than 10% effective path loss.
- Common per-node Discovery is **Multicast HELLO + Anti-Entropy gossip** across *all four candidates*. This is not an independent comparison of HyParView member selection or distributed rendezvous.
- Data plane variants are **inspired by** multicast, simple source-rooted tree, bounded sparse mesh and eager/lazy push; they are **NOT** HyParView, Plumtree, libp2p Gossipsub, Scribe, or NORM reference implementations. The topology knows node count and publisher IDs as benchmark scaffolding.
- Each case is **one seeded run**, not a confidence interval or general claim of performance.
- Node-specific membership warmup was 15 / 25 / 45 seconds for N=50 / 100 / 200. Data/recovery observation after that was 42 / 65 / 90 seconds and publishing was spread across 4 / 6 / 8 seconds. Thus direct timing comparisons across N are not like-for-like.
- Data payload was a fixed small 32-byte string inside JSON/UDP. All nodes published on the same Topic and subscribed to every source. This does not cover dynamic matching, partial subscriber interests, process crashes, multi-hop radio links, or actual hardware multicast behavior.
- No Zenoh or Cyclone DDS jobs ran in this workflow. Their previously identified benchmark configuration issues make earlier direct rankings unreliable.

## Technical observations

- Sparse Mesh obtained the highest *partial* receipt count in every 50/100/200 scenario. However its eager forwarding sends orders of magnitude more application datagrams (N=200, 0% loss: 271,020 mesh application-forwarding sends vs 400 origin multicast sends), so its extra redundancy is expensive even when bridge byte counters show smaller differences.
- For N=200, the baseline multicast and other repair variants emitted as many as about 53,800 NACK request datagrams, yet only a small fraction of successful origin response payloads were recorded. This signals a serious *implementation-specific recovery bottleneck*, not an algorithmic impossibility.
- Reported SO_RCVBUF / socket overflow and application send errors were zero in sampled runs, but this does not prove that the kernel bridge/qdisc or NIC delivery was loss free. The 0% configured loss cases can still suffer queueing and implementation drops.
- Full membership Discovery success does not prove individual publisher/subscriber *topic interest matching* in arbitrary configurations: this test hardcodes all-to-all subscriptions.

## Architecture recommendation

- **Provisional discovery baseline:** Multicast HELLO + Anti-Entropy for a single shared L2 LAN; 24/24 full membership convergence was measured here.
- **No user-data algorithm adoption:** none meets strict all-subscriber receipt; multicast and mesh are experimental comparison baselines only.
- Implement sender retention + receiver missing-range bitmap, controlled retransmission with feedback, end-to-end subscriber receipts, protocol-level pacing/backpressure, and qdisc/UDP receive drop telemetry. Rerun the same 50/100/200 workload before selecting the data forwarding substrate.
- For genuine comparisons of HyParView, Plumtree and Gossipsub, integrate faithful implementations and include realistic multi-hop and partial-topic subscription topologies.
