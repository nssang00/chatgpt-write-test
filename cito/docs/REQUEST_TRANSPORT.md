# Remote Request/Reply transport

Cito remote Request/Reply reuses the same request type identity, handler-demand
discovery, and RequestReplyCore used by the same-process API. It does not
introduce a parallel RPC runtime.

## CTX1 frame

The first transport envelope is versioned as `CTX1`.

```text
magic          4 bytes   "CTX1"
kind           u8        Request / Reply / Cancel
status         u8        RequestStatus
reserved       u16       zero
request_id     u64 LE
scope_id       u64 LE
resource_id    u64 LE
request_type   u64 LE
payload_size   u32 LE
payload        bytes
```

Request frames carry the exact RequestKey and require status=Ok. Reply and
Cancel frames carry an empty key. Cancel requires status=Cancelled and an empty
payload.

The codec is bounded by a 32-bit payload length and rejects malformed kind,
status, reserved bits, zero RequestId, invalid key placement, truncation, and
payload-length mismatches.

## Correlation

Outbound RequestIds are generated by the existing RequestReplyCore. The
transport stores the selected DestinationId and accepts a Reply only from that
expected peer.

Inbound correlation is keyed by:

```text
peer/session id + RequestId
```

This is important because two remote clients may both have RequestId=1 at the
same time. The peer/session identity comes from the secure transport session;
it is intentionally not duplicated into the wire frame.

Cancellation removes the inbound correlation so a late handler reply is
suppressed. Transport loss can fail all pending requests for one destination
as Unavailable.

## Destination selection

RequestTransportCore looks up the synthetic request-handler capability
DemandKey already discovered through HostRuntimeCore and chooses the smallest
DestinationId deterministically for the v1 baseline. No remote destination
means Unavailable without creating pending correlation state.

A future balancing policy can replace this selection rule without changing the
public `request()/handle()` API or the request correlation model.

## QUIC

Reliable remote Request/Reply uses a bidirectional QUIC stream. The current
MsQuic integration smoke verifies:

```text
client RequestTransportCore
    -> CTX1 Request
    -> QUIC bidirectional stream
    -> server RequestTransportCore
    -> RequestReplyCore handler
    -> CTX1 Reply
    -> same QUIC stream
    -> client completion
```

MsQuic receive callbacks copy bytes and post work to a small loop queue. They
do not execute RequestReplyCore or mutate discovery/request routing state
directly. This preserves the Cito ownership rule that runtime state is advanced
from the event-loop side.

The smoke seeds an already-discovered route; handler-capability discovery is
covered independently by DiscoveryControlCore regression. Public Context
network attachment is still a later integration gate.
